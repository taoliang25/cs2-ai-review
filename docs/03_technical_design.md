# 技术方案

- 文档版本：v0.1
- 更新日期：2026-11-04
- 依据样本：demoparser2 官方公开 `test_demo.dem`
- 当前结论：Awpy 作为主解析器，demoparser2 作为交叉校验器

## 1. 技术目标

系统首版采用本地单体架构，优先保证：

1. 能稳定解析单场常规 5v5 CS2 Demo。
2. 能从真实事件和位置数据计算可核验的行为指标。
3. 能完成玩家选择、全场分析、单回合下钻和证据展示。
4. 在没有大模型 API 时仍可生成模板报告。
5. 能记录解析器版本、指标版本、事实包和报告来源，便于复现。

首版不以高并发、公网部署、多用户账户或商业级容灾为目标。

本次单场粗略耗时：

- Awpy 载入回合、击杀、伤害、炸弹、投掷物、玩家、经济、射击、燃烧和烟雾数据约 1.7 秒。
- Awpy 生成全场逐秒快照约 0.8 秒。
- demoparser2 按 64 tick 采样位置和状态约 1.3 秒。

Awpy 逐秒快照不直接包含地图区域名称，但可通过原始字段
`m_szLastPlaceName` 获取 `TSpawn`、`CTSpawn`、`Middle`、`BombsiteA`
等真实地点标签，并与同一 tick 的位置快照关联。该字段已纳入事实层。

以上仅为开发机单次验证，不作为论文最终性能结论。

## 3. 选型结论

### 3.1 主解析器：Awpy

选择原因：

- 同时提供回合、经济、炸弹、投掷物、武器状态和位置快照，适合直接构建事实层。
- 已提供地图雷达、坐标映射和地图数据接口。
- 输出 Polars DataFrame，便于后续特征处理。
- 与 demoparser2 在关键事件计数上一致。
- 能稳定安装和运行在当前 Windows + Python 3.13 环境。

注意事项：

- `players` 表可能包含 `DemoRecorder`，必须通过 `side` 非空等规则过滤。
- 地图图片和雷达元数据需要提前下载并缓存，现场演示不应临时联网。
- 仍需使用用户最终持有的完整 Demo 重新验证。

### 3.2 交叉校验器：demoparser2

用途：

- 对玩家、回合、击杀、伤害和关键事件数量做抽样对照。
- 当 Awpy 某字段异常时查询原始事件，定位问题。
- 不承担首版主业务数据链路，避免两套解析结果长期分叉。

### 3.3 数据表与网页

- 数据清理与特征计算：Polars 为主；必要时使用 Pandas。
- 本地存储：SQLite。
- 网页：Streamlit。
- 可视化：Plotly 为主，雷达底图与位置热力图叠加。
- 规则特征版本管理：Python 模块 + 规则版本号。
- 可选机器学习：scikit-learn；仅在真实多场数据验证后加入。
- 可选树模型解释：LightGBM + SHAP；没有相应模型时不引入。
- 大模型：通过统一 `ReportProvider` 接口接入，API 与模型名称可配置。
- 报告降级：同一事实包交给模板报告生成器。

## 4. 总体架构

```text
Streamlit 页面
  |
  v
应用服务层
  |-- Demo 上传与校验
  |-- 玩家选择
  |-- 分析编排
  |-- 报告生成
  |
  +--> Awpy 解析适配器 ---> 事实归一化 ---> SQLite
  |                                  |
  |                                  +--> 规则指标计算
  |                                  +--> 关键回合排序
  |                                  +--> 事实包 FactBundle
  |
  +--> demoparser2 交叉校验（开发/诊断）
  |
  +--> ReportProvider
          |-- 模板报告
          `-- 可替换大模型 API
```

### 4.1 建议代码分层

```text
src/cs2_review/
  app.py                    # Streamlit 入口
  pages/                    # 上传、选玩家、总览、回合详情
  services/                 # 分析编排和报告用例
  parsers/                  # Awpy 主适配器、demoparser2 校验器
  analysis/                 # 特征、回合标签、关键回合、事实包
  reporting/                # 模板与 API Provider
  persistence/              # SQLite Repository
  visualization/            # 雷达图、热力图、时间线、经济图
  domain/                   # 数据对象和类型
tests/
data/
  demo/                     # 原始 Demo，不提交 Git
  interim/                  # 调试中间结果，不提交 Git
  processed/                # 本地 SQLite，不提交 Git
```

首版保持模块化单体，不增加 FastAPI 前后端分离的部署复杂度。如果后续需要公网接口，再把服务层暴露为 API。

## 5. 分析流水线

### 5.1 阶段一：解析与规范化

1. 计算 Demo SHA-256，形成稳定的分析标识。
2. 读取头部、回合、玩家、击杀、伤害、炸弹、投掷物、射击和经济。
3. 按 1 秒采样玩家位置、生命、护甲、现金、装备价值和状态。
4. 过滤观战者和非玩家记录。
5. 将世界坐标通过地图元数据转换为雷达图坐标。
6. 保存版本、解析状态和失败原因。

### 5.2 阶段二：事实指标

所有指标必须定义：

- 指标名和业务含义。
- 计算口径。
- 使用的数据表与字段。
- 时间窗口和空间区域。
- 证据 ID。
- 规则/模型版本。
- 样本量与缺失情况。

首批指标：

- 开局首个进入区域、前 15 秒路线、全场区域停留。
- 与最近队友距离、分离持续时间、跟队率。
- 首次交战时间、首次击杀/死亡、首杀参与次数。
- 投掷物类型、时间窗口、落点区域及是否与队友行动相邻。
- 优势、均势、劣势回合中的同类指标差异。
- 残局人数、剩余时间、信息和目标状态。
- 队友首次受击/交战时，玩家的距离、移动方向、到达和支援结果。
- 关键事件前后的人数、经济、控制和回合结果变化。

初版规则阈值必须通过样本观察后配置，不能先在论文中宣称准确性。

### 5.3 阶段三：战术模式与关键回合

首版以可解释规则完成模式识别：

- 早期抢区。
- 默认控图。
- 快速转点。
- 独立潜伏。
- 跟随主攻。
- 优势局主动压迫。
- 劣势局保枪或回防。
- 残局主动寻找信息和被动等待。

关键回合使用可解释评分，候选因素包括：

- 是否发生首杀或首死。
- 是否显著改变人数和经济优势。
- 是否成功支援队友。
- 是否发生目标事件。
- 是否属于赛点、经济转折或比分关键节点。
- 行为是否体现稳定的个人倾向。

评分结果必须展示贡献项，不能只给一个黑箱分数。

### 5.4 阶段四：事实包与报告

事实包是解析分析层与报告层之间的唯一接口。它只包含已计算内容和证据引用。

建议结构：

```json
{
  "schema_version": "1.0",
  "match": {
    "map": "de_mirage",
    "rounds": 10,
    "final_score": [9, 1]
  },
  "player": {
    "steamid": "...",
    "name": "...",
    "starting_side": "terrorist"
  },
  "metrics": [
    {
      "key": "opening_duel_rate",
      "value": 0.3,
      "sample_size": 10,
      "definition": "...",
      "evidence_ids": ["E-..."]
    }
  ],
  "key_rounds": [],
  "events": [],
  "allowed_inferences": [],
  "forbidden_claims": []
}
```

报告层输出至少包含：

- 可观测事实。
- 基于事实和行为规则的推断。
- 具体改进建议。
- 每条关键结论对应的证据 ID。

### 5.5 报告输出校验

报告生成后执行：

1. 校验所有证据 ID 是否存在于事实包。
2. 校验是否出现事实包中不存在的事件编号、比分或回合。
3. 校验样本不足的指标是否被写成确定性结论。
4. 检查是否出现“读心”“百分百还原真实意图”等不当表述。
5. 失败时回退到模板报告或标记为未通过。

## 6. 大模型接口

统一接口示例：

```python
class ReportProvider:
    def generate(self, fact_bundle: dict) -> ReportDraft:
        ...
```

实现：

- `TemplateReportProvider`：默认实现，不依赖网络。
- `OpenAICompatibleReportProvider`：通过配置提供地址、模型和密钥。
- 测试用 `FixedReportProvider`：只用于单元测试，不作为论文实验数据。

API 密钥只从环境变量读取，不写入代码、SQLite 或 Git。

大模型提示词分三部分：

- 系统约束：只能使用事实包，禁止补写比赛经过。
- 事实包：机器生成的结构化数据。
- 输出格式：固定 JSON Schema 或严格字段模板。

## 7. 算法与论文口径

### 7.0 已确认的技术重点

导师没有要求必须加入独立的机器学习算法创新。用户的核心需求是：

- 系统读取玩家 Demo。
- 基于真实对局内容总结玩家表现。
- 给出有依据、可理解的改进建议。

因此首版不把 scikit-learn、LightGBM 或 SHAP 作为必需组成。主方案保持
“事件特征 + 可解释规则 + 证据约束大模型/模板报告”。机器学习只作为以后
确有需要时的扩展，不以算法复杂度替代完整产品闭环。

### 7.1 首版优先内容

首版核心是可解释的事件特征与战术规则。它们负责真实数据计算，大模型负责解释，不把大模型当作事实来源。

### 7.2 非首版必需的学习模型

只有在获得多场可复现 Demo 和可靠标签后进行：

- 无监督聚类：发现打法类型或回合模式，用轮廓系数、稳定性和人工案例检查评估。
- 异常检测：识别偏离个人常态的异常决策，用案例回查和敏感参数分析评估。
- 有监督模型：只有当行为标签由明确规则或人工标注获得时使用，并报告标注一致性。
- 关键回合排序：优先生成可解释规则分数；改用学习排序模型时必须使用独立测试集。

### 7.3 防泄漏约束

- 数据划分必须按 Demo 分组，不能让同一场 Demo 的回合同时进入训练集和测试集。
- 区分“当时可用信息”和“事后结果”；预测当时决策的模型不得使用未来击杀或回合结果作为输入。
- 样本标准化参数只能在训练集拟合。
- 特征筛选、阈值选择和超参数调优都只能在训练/验证数据内进行。
- 最终报告应分别说明事件识别、行为标签和关键回合推荐的评价方式。
- 不能把规则生成的标签当作完美真值，再用同一规则评估模型准确率。

### 7.4 论文中不得声称

- 没有真实运行数据的准确率、F1 或用户满意度。
- Demo 可读取玩家真实想法。
- 单场比赛足以证明打法分类模型泛化。
- 大模型输出本身等于战术识别模型的准确率。

## 8. 性能与稳定性目标

暂定首版目标，需用最终 Demo 重新验证：

- 单场解析和核心特征计算在普通本科演示电脑上不超过 60 秒。
- 页面步骤均有明确处理中、成功或失败状态。
- 同一 Demo 和同一版本产生一致的分析结果。
- 地图资产、依赖和已验证 Demo 已缓存，现场演示不依赖实时下载。
- API 不可用时自动显示模板报告。

## 9. 当前技术风险

| 风险 | 应对 |
|---|---|
| 当前只有一个公开测试样本 | 继续寻找多场常规 5v5 Demo；最终至少用用户认可的真实 Demo 验证 |
| 当前样本以投降结束 | 不据此评估完整比赛或后期残局表现 |
| 地图坐标和区域名称需验证 | 使用官方地图数据或项目自定义区域多边形，并做可视化抽查 |
| 行为标签没有天然真值 | 公开规则、人工抽查、一致性和局限性说明，不伪造准确率 |
| 大模型调用不可用 | 模板报告为默认可用路径 |
| 单机环境端口冲突或依赖损坏 | 提供启动自检、固定依赖和离线缓存 |
