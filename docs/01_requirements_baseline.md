# 基于对局事件的《CS2》战术识别与赛后智能复盘系统

## 需求基线

- 文档版本：v0.1
- 更新日期：2026-11-04
- 当前阶段：需求梳理与 Demo 解析可行性验证前
- 项目性质：本科人工智能专业毕业设计原型系统
- 文档用途：记录已确认范围、形成后续设计基线，并集中管理尚未确认事项

> 本文只记录当前确认或明确建议的内容。技术路线、数据库结构和实验方案需在真实 Demo 验证后继续确定，避免在数据不可得时提前锁定实现。

## 1. 项目定位

本项目面向《CS2》常规 5v5 对局的个人赛后复盘，构建一个本地运行、演示稳定、逻辑闭环的网页原型。系统从用户上传的单场 Demo 中提取真实对局事件，选择一个玩家作为主要分析对象，结合其行动轨迹、行为习惯和关键决策，生成有事件证据支持的玩家画像、回合复盘和改进建议。

项目重点是：

1. 形成“上传 Demo—解析—选择玩家—生成画像与复盘—查看证据和单回合指导”的完整闭环。
2. 让分析建立在真实事件和可追溯统计数据之上，而不是让大模型自由编写比赛经过。
3. 用适合本科毕业设计和答辩的方式解释数据处理、规则/模型、特征选择、效果验证与系统限制。
4. 为玩家提供可以理解、可以行动的训练建议，而不仅是 K/D、评分等结果指标。

## 2. 用户与使用场景

### 2.1 主要用户

- 希望复盘自己单场表现的《CS2》玩家。
- 本科毕业设计答辩现场的教师和评审。
- 项目开发者本人，用于调试、实验复现和论文取材。

### 2.2 典型场景

1. 玩家上传一场自己的常规 5v5 对局 Demo。
2. 系统完成解析后展示本场玩家列表。
3. 玩家点击选择需要分析的玩家，并确认阵营和身份。
4. 系统生成该玩家的全场画像、关键回合和证据图表。
5. 玩家从全场总结进入某一回合，查看该回合的时间线、关键决策和替代方案。
6. 玩家查看 AI 复盘或模板报告，获得训练建议，并区分“可观测事实”和“行为推断”。

## 3. 已确认范围

### 3.1 游戏与对局范围

- 仅支持《CS2》。
- 仅支持常规 5v5 对局，例如竞技模式或 Premier。
- 不支持死亡竞赛、军备竞赛和 Wingman。
- 一次只分析用户上传的一场 Demo。
- 一次选择一个玩家作为主要分析对象。
- 分析可以覆盖整场，也可以下钻到单个回合。

### 3.2 分析重点

系统围绕所选玩家分析：

- 行动轨迹和区域偏好。
- 开局去向、常用路线和活动区域。
- 单走或跟队的倾向。
- 首杀尝试频率和主动交战倾向。
- 道具使用方式。
- 优势局与劣势局中的行为差异。
- 残局处理方式。
- 团队配合和支援意识。
- 关键动作对回合局势及比赛结果的影响。

以上内容应尽量从事件统计、轨迹和规则中计算，再由大模型解释，不由大模型自行补充未发生的细节。

### 3.3 报告内容

系统报告必须包含：

1. 本场玩家画像：打法风格、优势、坏习惯和主要问题。
2. 回合时间线：开局位置、路线、关键动作、交战和回合结果。
3. 关键决策分析：发生了什么、产生了什么影响、当时还有哪些可选方案。
4. 单回合复盘：同时覆盖优秀回合和导致失利或明显受损的回合。
5. 全场总结：最重要的三个问题及具体训练建议。
6. 证据展示：位置图、热力图、经济变化和关键事件。

### 3.4 AI 生成边界

- 大模型只接收由系统计算出的结构化事实、指标和证据片段。
- 报告中的比赛经过必须有事件编号、时间点或统计数据作为依据。
- Demo 无法读取玩家真实想法，因此只能使用“系统判断”“行为倾向”“可能意图”等措辞。
- 不得声称百分之百还原玩家心理或主观决策过程。
- 大模型 API 必须可替换。
- 无 API、API 失败或调用受限时，系统可以使用基于同一事实结构的模板报告完成闭环。
- AI 输出必须与事实数据一同展示，避免用户只看到不可核验的生成文本。

### 3.5 暂不纳入首版

- 王者荣耀、金铲铲之战、三角洲行动等其他游戏。
- 死亡竞赛、军备竞赛、Wingman 等非常规 5v5 模式。
- 多场历史记录对比和长期趋势分析。
- 同时分析多名玩家或双方全队技战术。
- 商业级用户运营、付费系统和大规模并发。
- 默认公网部署。
- 默认加入用户账号、上传历史记录和云端报告保存。

## 4. 目标使用流程

```text
打开网页
  -> 上传单场 CS2 Demo
  -> 校验文件并解析地图、回合和玩家列表
  -> 点击选择主要分析玩家
  -> 计算该玩家的真实事件、轨迹和统计特征
  -> 生成玩家画像、关键回合候选和全场总结
  -> 查看证据图表与回合时间线
  -> 进入单个回合查看关键决策和替代方案
  -> 导出或展示复盘报告（导出方式待确认）
```

### 4.1 前置条件

- 上传文件是受支持且完整的 CS2 常规 5v5 Demo。
- Demo 能被选定的解析库稳定读取。
- 系统能够获取必要的玩家标识、回合、事件、位置和经济信息。
- 如果 Demo 缺字段或解析失败，系统应明确提示，不能生成看似完整的虚假报告。

### 4.2 玩家选择

建议使用“解析后玩家列表点击选择”作为主交互，显示：

- 玩家名称。
- Steam ID 或平台可见标识（若 Demo 可提供）。
- 所属阵营和队伍。
- 本场基础统计。

文件和玩家身份的任何外部关联都应先确认隐私和学校要求。

## 5. 分析事实与分析表达

### 5.1 事实层

系统应优先保存可由 Demo 验证的数据：

- 对局元数据：地图、模式、比分、日期、Demo 标识。
- 玩家：名称、Steam ID（若可用）、阵营、队伍。
- 回合：开始/结束时间、比分、经济、获胜方、结束原因。
- 事件：击杀、死亡、助攻、投掷物、下包、拆包、伤害等解析库可提供的事件。
- 空间：采样时间点、位置、区域、朝向（若可用）。
- 经济：现金、装备价值、购买情况（以实际解析字段为准）。
- 派生指标：首杀参与、存活情况、区域停留、距队友距离、支援行为等。

### 5.2 表达层

大模型输入应采用“事实包”形式，至少包含：

- 分析对象及对局背景。
- 已计算指标及对应计算口径。
- 关键事件及其 ID、回合、时间和位置。
- 回合结果和局势变化证据。
- 允许的解读范围、禁止编造的要求。
- 输出格式和引用证据 ID 的要求。

事实包中不应包含无法由 Demo 支持的假设。如果某项指标未计算或置信度不足，报告应明确显示“暂无足够证据”。

### 5.3 分析维度口径

| 维度 | 可使用的真实证据 | 报告中的表达 |
|---|---|---|
| 开局去向 | 回合开始位置、首个区域进入、前若干秒轨迹 | “该回合从 CT/T 出生区进入 B 区”或“常接近 B 区” |
| 常用路线 | 空间采样序列、区域转移序列 | “常用路线偏向 A 长—A 点” |
| 活动区域 | 位置热力图、区域停留时间和回合覆盖率 | “活动集中在包点附近” |
| 跟队/单走 | 与队友距离、最近队友距离变化、分离时长 | “系统判断更倾向独立行动” |
| 首杀尝试 | 首个交战中是否为主动方、首次伤害/击杀时间 | “首杀尝试频率较高” |
| 交战倾向 | 交战次数、首次开火/伤害、距离、存活结果 | “更常主动发起近距离交战” |
| 道具使用 | 投掷物类型、时机、落点、是否造成效果或提供控制 | “更常使用烟封锁入口，较少使用闪光配合” |
| 优势/劣势差异 | 按比分差、经济差、人数差分层的同类指标 | “落后时单走比例相对上升” |
| 残局处理 | 人数差、剩余时间、信息获取、包点状态、最终结果 | “1v2 残局中倾向先保枪再寻找机会” |
| 支援意识 | 队友交战时的距离、路径、补枪、道具、治疗/掩护等可观测行为 | “队友首次交战时较远，支援到达滞后” |
| 关键影响 | 事件前后人数、经济、控制区域和回合结果变化 | “这次首杀让队伍获得人数优势并转化为回合胜利” |

具体阈值不能凭经验伪造。开发阶段应通过多种回合样本观察、规则验证和必要的敏感性分析确定；论文中必须报告阈值来源及局限。

## 6. 关键回合与决策分析

### 6.1 候选回合类型

关键回合候选应同时考虑正面与负面表现：

- 优秀回合：关键首杀、及时支援、有效残局、明显改变经济或比分走势的回合。
- 问题回合：可观测的关键失误、较晚支援、无收益单走、优势局处理不当等。
- 高影响回合：比分关键、经济转换关键或对比赛结果影响较大的回合。
- 代表性回合：能够体现玩家稳定行为倾向的回合。

### 6.2 单回合结构

每个单回合复盘至少包含：

1. 回合背景：地图、阵营、比分、经济、人数和关键目标状态。
2. 开局位置与路线。
3. 按照时间排序的关键动作、交战、道具和目标事件。
4. 对局势的可观测影响。
5. 行为推断：可能的风险、收益和决策倾向。
6. 可选方案：结合当时信息和位置给出合理备选，但必须标为“复盘建议”，不冒充当时唯一正确选择。
7. 证据入口：地图位置、热力图、经济变化和事件列表。

## 8. 非功能需求

### 8.1 稳定性

- 演示流程应能在本地一键或少量命令启动。
- 解析失败、字段缺失、AI API 失败都应可恢复或降级。
- 现场演示不应依赖必须联网的大模型 API。

### 8.2 可解释性

- 每个统计结论应能显示计算口径和证据来源。
- 关键回合推荐需能说明为什么入选。
- AI 复盘必须明确区分事实、统计推断和建议。
- 比赛过程不能由大模型脱离事件自由生成。

### 8.3 可复现性

- 保存依赖版本、解析库版本、关键参数、实验脚本和输入输出摘要。
- 实验结果必须由真实运行产生。
- 数据划分、特征生成和评估过程应能由论文和代码材料解释。

### 8.4 隐私与网络

- 默认优先本地上传、本地解析、本地保存。
- 不应把 Demo 或玩家身份信息未经确认发送给第三方服务。
- 大模型 API、外部网络和隐私限制需在实现前确认。

### 8.5 用户体验

- 对本科演示场景，页面重点是状态清楚、图表可读、流程可重复。
- 技术错误应转换为用户能理解的原因和建议。
- 不夸大分析能力，避免出现“准确还原真实想法”等表述。

## 9. 最小可行版本验收标准

首版 MVP 至少满足：

1. 使用一场真实、完整的 CS2 常规 5v5 Demo 跑通解析。
2. 页面展示地图、比分、双方玩家，并可选择单个玩家。
3. 所选玩家的关键轨迹、事件、经济变化和基础行为指标来自同一场 Demo。
4. 能展示玩家画像、全场总结、至少一个优秀回合和一个问题回合。
5. 单回合页面能显示时间线、可观测影响、行为推断和备选方案。
6. 关键结论至少关联一种证据，如事件编号、时间点、位置图或统计指标。
7. AI 不可用时，模板报告仍可生成并展示。
8. 演示流程可在本地重复完成，不使用伪造数据或预先编造的比赛文本。

## 12. 当前风险与应对

| 风险 | 影响 | 当前应对 |
|---|---|---|
| Demo 解析库或字段支持不稳定 | 无法闭环或某些指标缺失 | 先运行真实 Demo 字段验证，再做界面 |
| 不同来源 Demo 格式不同 | 现场演示不稳定 | 固定已验证 Demo 和解析环境，保留失败提示 |
| 行为标签缺乏真值 | 难以证明“战术识别准确率” | 明确区分事件事实、规则标签和统计推断；实验设计需真实验证 |
| 大模型编造比赛过程 | 报告不可信 | 事实包、证据 ID、输出校验和模板降级 |
| 首版范围过大 | 无法按期完成 | 按 MVP、增强、可选三级冻结范围 |
| 论文要求与当前方案不一致 | 后期返工 | 尽早取得任务书和模板，只问当前最必要的信息 |

## 13. 变更规则

- 已确认需求发生变化时，更新本文版本并记录原因和影响。
- 新增功能必须先判断是否影响“上传单场 Demo—选择单玩家—有证据复盘”的主闭环。
- 任何无法获得真实数据支持的指标、实验或结论不得进入最终系统或论文。
